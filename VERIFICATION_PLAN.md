# Verification and validation plan

**Draft · 2026-11-03. All tests NOT RUN.** Test IDs correspond to [requirements](SPEC.md) and [tasks](IMPLEMENTATION_PLAN.md); [architecture](ARCHITECTURE.md) defines records. Verification checks implementation against the contract; experimental validation tests model predictions against independent measurements. Neither a smooth grid nor solver convergence alone establishes physical accuracy.

## Exploratory versus acceptance runs

**Exploratory development/spikes:** use training/development cases only, including topology and solver feasibility or reuse comparisons. Record `NON-ACCEPTANCE`, purpose, code/tool versions, inputs, settings, outputs and failures. Thresholds may be provisional or absent; such runs cannot support acceptance or release-pass claims. An independent custodian seals held-out cases before development; explorers cannot select, inspect or consume them. Preliminary findings may inform the first acceptance contract, with their provenance recorded.

**Acceptance:** before each numerical acceptance or optional physical assessment, independent reviewers approve and sign an immutable test contract and content hash. It binds the candidate code, selected topology, corpus split, solver/configuration where applicable, metrics, limits, resources, analysis and failure policy. The runner blocks missing, unsigned, mismatched or modified contracts. A custodian runs or releases the held-out cases only after this freeze and records access. No exploratory result is retrospectively reclassified as acceptance.

Use versioned `thresholds.json` and a linked corpus manifest. Required fields: `schema_version`, `revision`, `run_kind`, `approved_by`, `approved_at`, `candidate_hash`, `family_contract_hash`, `corpus_manifest_hash`, `solver_name/version/config_hash` (or explicit `not_applicable`), `hardware_threads`, and per metric `case_id`, `geometry_hash`, `flow_conditions_with_units` (or `not_applicable`), `metric`, `definition`, `unit`, `acceptance_operator`, `limit`, `uncertainty_method`, `reference_or_baseline`, and `rationale`. Numerical acceptance specifies held-out success rate and failure policy, residual reduction, mass imbalance, QoI stability, refinement differences, wall-resolution policy, elapsed time, memory and repeatability tolerances. Only an optional experimental assessment needs physical comparison thresholds, measurement uncertainty and data permissions; absence does not block numerical release. Every applicable threshold is frozen before its acceptance run, not before exploratory work. Thresholds are engineering choices, not invented literature values.

Maintain append-only contract revisions, signatures, run logs, outcomes and justifications. Failed results remain failed under the original contract. Never loosen a threshold or revise selection after seeing results and call the old run a pass. Changes require a new reviewed contract and new acceptance run; if the team has seen held-out outcomes and changes the candidate, limits or selection based on them, that set is contaminated for the new claim and an independent custodian must supply a fresh untouched held-out set. If none is available, the new acceptance claim is blocked. The prior results and exposure history remain public in the evidence record, subject to data rights.

Example proposed numerical defaults, subject to acceptance-contract approval, are single-thread pinned repeatability and positive signed Jacobian greater than `1e-12 * chord²` at all bilinear reference-cell corners. Bilinear quad determinant is affine in reference coordinates, so corner positivity establishes local positivity throughout the reference square; separately check nonadjacent-cell overlap, intersections and domain coverage. The floor is an engineering safeguard, not an accuracy guarantee. Freeze tolerances and absolute budgets for acceptance; no universal physical limit is asserted here.

## Test matrix

| Test | Method and pass criterion |
|---|---|
| V01 | Verify exploratory runs are labeled and cannot access held-out cases. Acceptance runner rejects missing, unsigned, modified or mismatched contracts; simulate a post-result threshold change and assert old failure persists and fresh hold-out is required. |
| V02 | Compare licensed alternatives on shared exploratory cases, logging versions, inputs, success/failure, effort, runtime and quality. Spike O-grid branch and seam feasibility; review a selected topology/reuse decision including unavailable alternatives. No exploratory comparison is acceptance evidence. |
| V03 | Table/property tests for NaNs, wrong dimensions/units, open and crossed contours, zero chord/pitch, periodic overlap and bounds; each returns correct location/status. Valid dimensional rescaling preserves normalized geometry. |
| V04 | Verify the P0-selected graph and feature/branch constraints, positive counts, seam coincidence and periodic bijection under `(0,pitch)`; reversed correspondence and missing seam fail. If the four-block hypothesis is selected, assert exactly four connected blocks. |
| V05 | Export known quads; parse with an independent reader, compare node coordinates, oriented cell connectivity, boundary edges/names, units and sidecar transform. Reject missing markers or malformed mapping; solver import is separately checked in V13. |
| V06 | Assert prescribed first height, count and geometric growth within frozen tolerances; zero/negative lengths and nonfeasible total thickness return failure, not adjusted hidden values. |
| V07 | Cross layer rays, collide with blade/periodic image, and test a near miss; collision prevents `OK` and solver-ready export. |
| V08 | Test inverted, concave/folded, degenerate, overlapping and gapped meshes against independent Jacobian and intersection checks; inspect reported offending indices and full boundary coverage. |
| V09 | Force repair convergence and nonconvergence; check iteration, displacement, elapsed and memory limits, immutable protected boundaries, and complete quality recheck after every accepted repair. |
| V10 | Repeat fixed update sequences on a pinned platform; compare canonical bytes, path and metrics, run on a second platform using frozen tolerances. Force incompatible updates and budget exhaustion; never accept invalid mesh. |
| V11 | Change geometry, pitch, units, options, thresholds, seed and algorithm/dependency versions individually; assert invalidation; compare cached versus fresh results and diagnostics. |
| V12 | Exercise deformation, repair and remesh branches; assert sensitivity status and that no gradients are presented as validated. |
| V13 | With the frozen numerical contract, assess geometry validity and held-out robustness, then ingest each training and untouched held-out mesh in a pinned solver at three systematically refined levels. Report residuals, mass imbalance, QoI stability, solved y+ distribution, QoIs and changes vs baseline; apply limits and include all failures. No solver convergence means no pass. |
| V14 | Optional physical assessment: compare preregistered pressure/loss or other measured QoIs at matched conditions with rights-cleared independent experimental data and uncertainties. Record mesh, iterative and measurement uncertainty, model-form limits and held-out outcomes; no data or unmet tolerance blocks the application claim, not library release. |
| V15 | A non-author follows clean-install and reproduction instructions on an independent environment; compare numerical evidence under frozen tolerances. Review licenses, rights for distributed data, maintainer ownership and issue/security process. T14 is not a prerequisite. |

Planned command examples such as `viscous-mesh verify --manifest corpus.json --thresholds thresholds.json` and `viscous-mesh benchmark --manifest corpus.json` are design sketches only: neither command exists or has been run. Acceptance mode must refuse unfrozen contracts regardless of invocation; explicitly labeled exploration may run without them and without held-out access. Track full versions, inputs, failed cases, logs and output hashes for every future run.
